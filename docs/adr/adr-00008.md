# ADR-008: Vendored `wayland-cursor` Patch for the Termux/Android Build

**Status:** Accepted
**Date:** 2026-06-21
**Deciders:** Kevin (project lead)

---

## Context

`waymux-bridge` must be cross-compilable to `aarch64-linux-android` (Termux) —
see the architecture constraints in `AGENTS.md`. Building it (or natively in
Termux) fails to compile a transitive dependency:

```
error[E0432]: unresolved import `rustix::shm`
  --> wayland-cursor-0.31.14/src/lib.rs:62:5
   |
62 | use rustix::shm;
   |     ^^^^^^^^^^^ no `shm` in the root
   |
note: found an item that was configured out
  --> rustix-1.1.4/src/lib.rs:289:9
   = the item is gated here (cfg(not(any(..., target_os = "android", ...))))
```

Chain of causes:

1. `smithay-client-toolkit` (ADR-003/ADR-007, the bridge's Wayland client)
   depends on **`wayland-cursor` non-optionally** — there is no feature flag to
   drop it, in 0.19 or 0.20.
2. `wayland-cursor` 0.31.x imports `rustix::shm` **unconditionally** at module
   scope, and uses it only for a `shm_open`/`shm_unlink` fallback in
   `create_shm_fd`.
3. `rustix` gates its entire `shm` module out on `target_os = "android"` (it has
   done so since at least 1.0.0 — bionic does not provide POSIX
   `shm_open`/`shm_unlink`). So the import does not resolve on Android.

Notably, `wayland-cursor`'s Android **runtime** path does not need `shm` at all:
on Linux/Android it creates the buffer with `memfd_create` and only falls back
to `shm_open` on other Unixes. The breakage is purely the unconditional import
(and the dead fallback) being compiled on Android.

Options considered:

1. **Pin `rustix`** to a version exposing `shm` on Android — impossible; the
   module has been Android-gated across all 1.x releases.
2. **Drop or replace `smithay-client-toolkit`** in the bridge — large refactor;
   the bridge genuinely uses SCTK's `RegistryState`, `OutputState`, `Shm`, and
   `RawPool` for screencopy.
3. **Upgrade SCTK** — both 0.19 and 0.20 keep `wayland-cursor` as a hard
   dependency, so this does not help.
4. **`[patch.crates-io]` to a vendored copy** carrying a minimal `#[cfg]` fix.

---

## Decision

Vendor `wayland-cursor` 0.31.14 verbatim under `third-party/wayland-cursor/` and
redirect the dependency with a workspace-root `[patch.crates-io]` entry. The only
source change `#[cfg]`-gates the Android-incompatible code off
`target_os = "android"`:

- `use rustix::shm;`, `use rustix::fs::Mode;`, and
  `use std::time::{SystemTime, UNIX_EPOCH}` are gated `cfg(not(target_os =
  "android"))` (they are used only by the `shm_open` fallback).
- The `shm_open` fallback block in `create_shm_fd` is gated `cfg(not(target_os =
  "android"))`; on Android the function returns an `Unsupported` error if
  `memfd_create` is unavailable (effectively unreachable in practice).

No behavioural change on any existing platform: the Linux/macOS/BSD code paths
are byte-identical to upstream.

---

## Rationale

- A vendored `[patch.crates-io]` override is **self-contained** (no external
  fork, no network dependency at build time) and reproducible, which matters for
  Termux and CI alike.
- The patch is **minimal and mechanical** — only `#[cfg]` attributes — so keeping
  it in sync with upstream version bumps is low-effort. The manifest header and
  this ADR document why it exists.
- It is the smallest change that satisfies the "bridge must cross-compile to
  `aarch64-linux-android`" constraint without disturbing the SCTK-based capture
  design (ADR-003, ADR-007).

---

## Consequences

- New `third-party/` directory holds vendored third-party code. The crate is
  **not** a Cargo workspace member; it is pulled in solely via
  `[patch.crates-io]`. As a non-primary dependency it is lint-capped, so the
  CI `cargo clippy --all-targets --all-features -- -D warnings` gate does not
  apply to it.
- The vendored crate retains upstream's MIT license (`LICENSE.txt`) and is
  exempt from this repo's house style (300-line limit, no-`unwrap`, rustdoc
  rules) as verbatim third-party code.
- **Maintenance:** when bumping `smithay-client-toolkit`/`wayland-cursor`,
  re-vendor the matching `wayland-cursor` release and re-apply the two `#[cfg]`
  edits, or drop the patch entirely once upstream gates the `shm` usage itself
  (track Smithay/wayland-rs). The version in `third-party/wayland-cursor/
  Cargo.toml` must stay semver-compatible with what SCTK requests.
- Verified: `cargo check -p wayland-cursor --target aarch64-linux-android`
  compiles, and the host workspace build + clippy gate pass.
