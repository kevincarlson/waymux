# ADR-008: Vendored Wayland Crate Patches for the Termux/Android Build

**Status:** Accepted
**Date:** 2026-06-21
**Deciders:** Kevin (project lead)

---

## Context

`waymux-bridge` must be cross-compilable to `aarch64-linux-android` (Termux) —
see the architecture constraints in `AGENTS.md`. Building the workspace there (or
natively in Termux) fails to compile two of the bridge's Wayland dependencies
with the same root cause:

```
error[E0432]: unresolved import `rustix::shm`
  --> wayland-cursor-0.31.14/src/lib.rs:62:5
error[E0432]: unresolved import `rustix::shm`
  --> smithay-client-toolkit-0.19.2/src/shm/raw.rs:8:5
note: found an item that was configured out
   = the item is gated here (cfg(not(any(..., target_os = "android", ...))))
```

Chain of causes:

1. `rustix` gates its entire `shm` module out on `target_os = "android"` (it has
   done so since at least 1.0.0 — bionic does not provide POSIX
   `shm_open`/`shm_unlink`). So any `use rustix::shm` fails to resolve on Android.
2. `wayland-cursor` 0.31.x imports `rustix::shm` **unconditionally** at module
   scope, using it only for a `shm_open`/`shm_unlink` fallback in
   `create_shm_fd`. Its Android **runtime** path already uses `memfd_create`, so
   the breakage is purely the unconditional import + dead fallback.
3. `smithay-client-toolkit` (ADR-003/ADR-007, the bridge's Wayland client)
   has the same unconditional `rustix::shm` import in `shm/raw.rs`, **and** only
   tries `memfd_create` on `target_os = "linux"` — on Android it skips memfd and
   falls straight through to the (now non-existent) `shm_open` path. The bridge
   uses SCTK's `RawPool`/`Shm` directly, so this code is genuinely reached.
4. SCTK depends on `wayland-cursor` **non-optionally** (no feature flag drops it,
   in 0.19 or 0.20), so it cannot be sidestepped via features.

Options considered:

1. **Pin `rustix`** to a version exposing `shm` on Android — impossible; the
   module has been Android-gated across all 1.x releases (and the 0.38.x line
   SCTK uses).
2. **Drop or replace `smithay-client-toolkit`** in the bridge — large refactor;
   the bridge genuinely uses SCTK's `RegistryState`, `OutputState`, `Shm`, and
   `RawPool` for screencopy.
3. **Upgrade SCTK** — both 0.19 and 0.20 (and master) keep `wayland-cursor` as a
   hard dependency and keep the same Linux-only `memfd` / Android-broken `shm`
   logic, so this does not help.
4. **`[patch.crates-io]` to vendored copies** carrying minimal `#[cfg]` fixes.

---

## Decision

Vendor both crates verbatim under `third-party/` and redirect them with
workspace-root `[patch.crates-io]` entries:

- `third-party/wayland-cursor/` (0.31.14)
- `third-party/smithay-client-toolkit/` (0.19.2)

The only source changes `#[cfg]`-gate the Android-incompatible code off
`target_os = "android"`:

**`wayland-cursor/src/lib.rs`**
- `use rustix::shm;`, `use rustix::fs::Mode;`, and
  `use std::time::{SystemTime, UNIX_EPOCH}` are gated `cfg(not(target_os =
  "android"))` (used only by the `shm_open` fallback).
- The `shm_open` fallback in `create_shm_fd` is gated `cfg(not(target_os =
  "android"))`; on Android the function returns an `Unsupported` error if
  `memfd_create` is unavailable (effectively unreachable in practice).

**`smithay-client-toolkit/src/shm/raw.rs`**
- `use rustix::shm::{Mode, ShmOFlags};` and `use std::time::{SystemTime,
  UNIX_EPOCH}` are gated `cfg(not(target_os = "android"))`.
- `create_memfd()` and the `memfd_create` branch of `create_shm_fd()` are
  extended from `cfg(target_os = "linux")` to `cfg(any(target_os = "linux",
  target_os = "android"))` so Android uses memfd as its primary path.
- The `shm_open` fallback is gated `cfg(not(target_os = "android"))`, with the
  same `Unsupported` error on Android if memfd is missing.

No behavioural change on any existing platform: the Linux/macOS/BSD code paths
are byte-identical to upstream.

The two vendored crates are listed in `workspace.exclude` so workspace-wide
`cargo fmt --all` / `clippy` / `test` do not treat them as members; they are
pulled in solely via `[patch.crates-io]`.

---

## Rationale

- A vendored `[patch.crates-io]` override is **self-contained** (no external
  fork, no build-time network dependency) and reproducible, which matters for
  Termux and CI alike.
- The patches are **minimal and mechanical** — only `#[cfg]` attributes — so
  keeping them in sync with upstream version bumps is low-effort. Each vendored
  manifest carries a header pointing back to this ADR.
- It is the smallest change that satisfies the "bridge must cross-compile to
  `aarch64-linux-android`" constraint without disturbing the SCTK-based capture
  design (ADR-003, ADR-007).

---

## Consequences

- A new `third-party/` directory holds vendored third-party code, excluded from
  the workspace and consumed only via `[patch.crates-io]`. As non-primary
  dependencies they are lint-capped: their warnings are not promoted to errors
  by the CI `cargo clippy ... -- -D warnings` gate (verified), and
  `cargo fmt --all` / `cargo doc --no-deps` skip them.
- Each vendored crate retains upstream's MIT license (`LICENSE.txt`) and is
  exempt from this repo's house style (300-line limit, no-`unwrap`, rustdoc
  rules) as verbatim third-party code.
- **Maintenance:** when bumping `smithay-client-toolkit` / `wayland-cursor`,
  re-vendor the matching releases and re-apply the `#[cfg]` edits, or drop a
  patch entirely once upstream gates its `shm` usage on Android (track
  Smithay/wayland-rs and Smithay/client-toolkit). Vendored versions must stay
  semver-compatible with what the dependency graph requests.
- Verified on this branch: `cargo check -p wayland-cursor
  --target aarch64-linux-android` and a `--target aarch64-linux-android` check of
  the vendored SCTK (`--no-default-features --features calloop`) both compile;
  the host workspace build and `cargo clippy --all-targets --all-features --
  -D warnings` gate pass. (A full bridge Android build additionally needs the
  Android NDK clang for `zstd-sys`, which is present in a real Termux
  environment.)
