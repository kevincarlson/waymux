# ADR-007: Bridge Wayland-Client Dependencies (dlopen, SCTK without xkbcommon, calloop)

**Status:** Accepted
**Date:** 2026-06-21
**Deciders:** Kevin (project lead)

---

## Context

Implementing the bridge's `wlr-screencopy` capture and `wlr-virtual-pointer`
injection (ADR-003 chose `smithay-client-toolkit` for the Wayland client) raised
three concrete build/runtime decisions.

1. **Linking libwayland.** Building `wayland-client` against a system
   `libwayland-client` requires the `-dev` package at link time, which is not
   always present (e.g. CI, and minimal Termux installs vary).
2. **SCTK's `xkbcommon` requirement.** SCTK's default features compile against
   the system `xkbcommon` (via `pkg-config`), which the bridge does not need —
   it injects keys through the virtual-keyboard protocol, not SCTK's seat.
3. **Event loop.** Screencopy capture and input injection must be driven
   together (Wayland socket events + an inbound input channel).

---

## Decision

- Depend on **`wayland-backend` with `client_system` + `dlopen`** so libwayland
  is loaded at **runtime** via `dlopen`; the bridge links without libwayland
  dev files.
- Set **`smithay-client-toolkit` `default-features = false`** (workspace-wide,
  bridge-only consumer) and enable only `calloop`. This drops the `xkbcommon`
  build dependency while keeping registry/output/shm.
- Drive capture + injection on one **`calloop`** event loop
  (`calloop-wayland-source` for the Wayland queue, a `calloop::channel` for
  inbound WIP), running on a dedicated thread bridged to the tokio pipeline.

---

## Rationale

- **dlopen** removes a hard link-time system dependency and matches how Termux
  X11/Wayland companions typically load libwayland. The runtime cost (one
  `dlopen`) is negligible, and it lets the whole stack `cargo check`/build on a
  host without libwayland `-dev`.
- Disabling SCTK defaults avoids pulling `xkbcommon`/`pkg-config` for a feature
  the bridge never uses, simplifying the build everywhere.
- `calloop` is SCTK's native event loop and cleanly multiplexes the Wayland fd
  with the injection channel and a frame-pacing timer — the pattern ADR-003
  anticipated for bridging calloop and tokio.

---

## Consequences

- New workspace dependencies: `wayland-backend` (dlopen), `wayland-protocols-wlr`
  (now used), `calloop`, `calloop-wayland-source`. `wayland-protocols-misc` is
  reserved for keyboard injection (not yet implemented) and is **not** currently
  a bridge dependency.
- libwayland must be present at **runtime** (it is, on any Wayland system /
  Termux Wayland setup). A missing compositor is reported as a clean startup
  error (exit code 3), not a link failure.
- The capture thread owns all Wayland objects; the tokio side communicates with
  it only through the frame channel (out) and the input channel (in).
